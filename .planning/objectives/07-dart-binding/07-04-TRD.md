<objective>
Prove the bindings are faithful (DART-05): run a shared subset of Objective 0's conformance corpus THROUGH the compiled artifacts — press.wasm (07-02, via Node) and the host-arch libpress.so (07-01, via cgo dlopen) — using the SAME JSON entrypoint the Dart code uses, and assert each boundary reproduces in-process press.Render output losslessly.

Purpose: the JSON boundary is the whole surface a Flutter client trusts; DART-05 verifies it doesn't drop or corrupt any part of press.Output. RESEARCH §6 grounds this in the existing `conformance/runner` seam — `RenderFunc` is already engine-agnostic, so this is a third (WASM) + fourth (capi) `RenderFunc` calling the compiled artifact. The WASM lane is the easiest to automate (Node, no emulator); the capi lane uses a host-arch c-shared rebuild (RESEARCH §6 / Pitfall 4 — the mobile `.so`/`.a` are ARM device ABIs that can't run on generic CI, so validate the identical cgo shim via a host-arch build; on-device smoke stays a separate later lane).
Output: `bind/conformance/subset.go` + a Node runner + WASM + capi boundary tests reusing `runner`/`htmldiff`.
</objective>

<anti_patterns>
- Do NOT call bind/capi/core.RenderJSON directly in the capi lane — that would bypass the cgo boundary entirely (the whole point is to exercise PressRender's C-string marshalling + memory ownership, the exact path dart:ffi uses). Go THROUGH the dlopen'd .so.
- Do NOT try to run the actual Android `.so` / iOS `.a` on the CI host — they are ARM device ABIs (RESEARCH Pitfall 4). Use the host-arch c-shared build (build-capi-host.sh). On-device/emulator smoke is a separate, later, small lane — not this corpus-scale test.
- Do NOT modify conformance/runner or htmldiff — reuse them unchanged (the seam is already engine-agnostic).
- Do NOT compare against the Marp golden as the PRIMARY signal — press-vs-Marp conformance is other objectives' concern. The boundary assertion is boundary-output == in-process-press.Render-output (parity), isolating "the boundary is lossless" from "press matches Marp".
- Do NOT select a plain-CommonMark-only subset — the boundary must be stressed across the whole Output shape (Model, CSS, math raw content, code, notes), so every battery must appear (RESEARCH §6).
- No LLM-generated cases: reuse the EXISTING hand-seeded corpus (Objective 0, Marp-derived). No property-based libs; descriptive named subtests (t.Run per case ID).
</anti_patterns>
