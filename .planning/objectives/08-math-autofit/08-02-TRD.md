<objective>
Patch the in-repo latex2mathml fork (internal/latex2mathml/, vendored by 08-01) for the two fork-only converter root-causes — big-operator limit stacking and `\sqrt[n]` radicand loss — and lock each with a structural MathML-DOM regression assertion in press/math/math_test.go. These are the two bugs research traced to information genuinely lost/misassembled inside the token walk before `Convert()` returns, so no output-side shim can fix them (research Architecture Patterns "Fork-required pattern"). Together they close 4 of the 8 PROPOSAL §11 spike cases (\sum, \prod, \lim, \sqrt[3]).

Purpose: RESOLVED DECISION #1, in-fork path. Sequenced FIRST of the two converter TRDs because these are the highest-risk, fork-only fixes; the empirical movablelimits check (Open Q1) is task 1 so the fix mechanism is chosen before code is written.
Output: patched converter.go (big-op tag/movablelimits) + walker.go (sqrt root-index read order) + 4 structural regression cases.
</objective>

<codebase_examples>
**Big-operator tag selection — the exact conditional to extend (internal/latex2mathml/converter.go ~lines 359-368):**
```go
var tag = style.Tag
if command == SUBSUP && len(node.Children) > 0 && node.Children[0].Token == GCD {
    tag = "munderover"
} else if command == SUPERSCRIPT && (modifier == LIMITS || modifier == OVERBRACE) {
    tag = "mover"
} else if command == SUBSCRIPT && (modifier == LIMITS || modifier == UNDERBRACE) {
    tag = "munder"
} else if command == SUBSUP && (modifier == LIMITS || modifier == OVERBRACE || modifier == UNDERBRACE) {
    tag = "munderover"
} else if (command == XLEFTARROW || command == XRIGHTARROW) && len(node.Children) == 2 {
    tag = "munderover"
}
```
Big operators (`\sum`, `\prod`, `\int`, `\oint`, `\bigcup`, `\bigcap`, `\bigvee`, `\bigwedge`, `\bigoplus`, `\bigotimes`, `\bigodot`, `\biguplus`, `\bigsqcup`) in display mode conventionally auto-stack WITHOUT an explicit `\limits`. This list doesn't cover that case → `\sum_{i=1}^n` in `$$…$$` emits side-by-side `msubsup`.

**Open Q1 hint — the converter ALREADY emits movablelimits for a related class (converter.go ~line 640):**
```go
} else if slices.Contains(SUB_LIST, token) {
    element := parent.CreateElement("mo")
    element.CreateAttr("movablelimits", "true")   // <-- precedent: it knows this attribute
```
`SUB_LIST` (converter.go:14) = `{DETERMINANT, GCD, INTOP, INJLIM, LIMINF, LIMSUP, PR, PROJLIM}` — the `\lim`-family. Big operators aren't in it. The check for Open Q1: does a display-mode `<mo movablelimits="true">∑</mo>` with a sub+superscript stack in headless Chromium? If yes, emitting movablelimits is the smaller fix. If uncertain, switch the tag to munderover (guaranteed — PROPOSAL §11 corrected.png verified munderover stacks).

**`\sqrt[n]` radicand loss — walker.go SQRT branch (~lines 306-328):** the code grabs "the next token" which for `\sqrt[3]{x}` returns the `[` OPENING_BRACKET, reads the bracket contents as the index ("3"), but never makes a SECOND read for the radicand `{x}` — it reuses the bracket-marker node as the radicand when building `Node{Token: ROOT, Children: append([]Node{nextNode}, rootNodes...)}`. Fix: read the bracket-index fully (to CLOSING_BRACKET), THEN a second `processToken` for the actual base; build ROOT with children [base, index]. MathML `<mroot>` child order is [base, index] (base first).

**The test pattern to extend (press/math/math_test.go TestMathML) — parse + assert element shape:**
```go
block := renderMathML(`\frac{a}{b}`, true)
if !strings.Contains(block, "<mfrac>") { t.Errorf(...) }
```
For structural precision beyond substring, parse with encoding/xml and assert child count/order (e.g. `<mroot>` has exactly 2 element children, first is the radicand). `renderMathML(raw, block bool)` is the entry point (block=true → display="block").
