<codebase_examples>
`github.com/yuin/goldmark-emoji@v1.0.6` (build-compat with goldmark v1.8.4 proven in 03-01's spike gate) supplies the shortcode half. Its `emoji.New(...)` is a `goldmark.Extender`:

```go
package press

import (
    "github.com/yuin/goldmark"
    "github.com/yuin/goldmark-emoji"
    "github.com/yuin/goldmark-emoji/definition"
    east "github.com/yuin/goldmark-emoji/ast"
)

// emojiOption returns the goldmark.Option bundle press.Render folds into
// NewEngine(pressExtraOpts...). It wires goldmark-emoji's Twemoji rendering
// method (shortcode half) PLUS the bespoke unicode-literal parser (below).
func emojiOption() goldmark.Option {
    return goldmark.WithExtensions(
        emoji.New(
            emoji.WithRenderingMethod(emoji.Twemoji),
            // emoji.WithTwemojiTemplate(...) — configurable base/ext (Marp's contract)
        ),
        unicodeEmojiExtender{}, // registers the bespoke InlineParser below
    )
}
```

The bespoke unicode-literal parser (research Don't Hand-Roll row 2): goldmark-emoji's `definition.Github()` carries unicode-bearing entries (`(*definition.Emoji).Unicode` / `IsUnicode()`). Build a rune-sequence → `*definition.Emoji` reverse index ONCE, then a `parser.InlineParser` whose `Trigger()` returns the lead bytes of emoji runes, which on match emits `east.NewEmoji(<shortname>, theEmoji)` — the SAME node type goldmark-emoji's own `emojiHTMLRenderer` renders. Only the trigger + lookup is new; the render path is reused verbatim.

```go
// emoji_unicode.go (sketch)
type unicodeEmojiExtender struct{}
func (unicodeEmojiExtender) Extend(m goldmark.Markdown) {
    m.Parser().AddOptions(parser.WithInlineParsers(
        util.Prioritized(newUnicodeEmojiParser(definition.Github()), 0), // low number → early
    ))
    // NOTE: goldmark-emoji already registers the NodeRenderer for east.Emoji;
    // do NOT register a second one — reuse it.
}
```

<anti_patterns>
- Do NOT hand-roll a shortcode table or `:`-trigger parser — goldmark-emoji already does trigger detection, the `definition.Github()` shortcode table, and a first-class `Twemoji` render method (research Don't Hand-Roll row 1).
- Do NOT register a SECOND NodeRenderer for `east.Emoji` — goldmark-emoji's Extend already registers one. The bespoke piece adds only an InlineParser and emits the existing node kind (research: "reusing its AST node + renderer means only the trigger/lookup logic is new").
- Do NOT emit a raw `<img>` string from the unicode parser — emit `east.NewEmoji(...)` so twemoji output is identical between shortcode-origin and unicode-origin emoji (one render path, one sanitize allow-list rule).
- Do NOT hardcode a twemoji CDN with no override — keep `base`/`ext` configurable (Marp's contract; matters for self-hosting / air-gapped, FEATURES.md).
</anti_patterns>

<error_recovery>
- If a literal-unicode rune renders as plain text (parser never fired): the `Trigger()` bytes don't cover that emoji's leading UTF-8 byte, or the InlineParser priority is too high. Emoji runes are multi-byte; base the trigger on the set of distinct leading bytes across `definition.Github()`'s unicode entries, and greedily match the longest rune sequence (ZWJ sequences, skin-tone modifiers, regional indicators are multi-rune — match longest-first).
- If a shortcode renders as plain `:smile:`: goldmark-emoji's extension wasn't added, or WithRenderingMethod wasn't Twemoji — confirm `emoji.New(...)` is in WithExtensions.
- If build fails on goldmark-emoji: 03-01's compat spike should have caught this. Re-check the spike; do NOT go mod tidy.
- ZWJ/skin-tone edge cases are a KNOWN long tail — cover the common single-rune emoji for baseline; note multi-rune ZWJ sequences as a documented baseline limitation if they don't reverse-index cleanly (do not block CORE-06 on exhaustive ZWJ coverage).
</error_recovery>
